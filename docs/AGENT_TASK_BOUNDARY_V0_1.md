# Agent Task Boundary v0.1

**Status:** typed binding and offline conformance contract. Not a production task runner, live egress enforcer, or security certification.

## 1. Purpose

Bind a high-risk agent task to one exact execution identity and one separately authorized network policy. The intended object is:

`tenant / Holon + task + principal + task-plan digest + pinned guest artifact + plan receipt + independent OCI source-consistency snapshot + workload identity + candidate/boundary policy proof + compiled policy + expiry + owner signature`

The contract is designed for the ARTEX-like capability class: planner/worker systems that may spawn children, enumerate assets, invoke tools, retain task memory and iterate after an initial goal. It does not depend on ARTEX names, ports, User-Agents, model providers, or scanner signatures.

## 2. Current Nixward primitives reused

| Existing primitive | What it establishes | What it does not establish |
|---|---|---|
| Software Ingress Covenant | S2/S3 artifact identity, guest permissions, digest-bound plan | That an agent task is authorized or that every runtime control is active |
| Rootless OCI guest launcher | Rootless Podman command, digest-pinned image, read-only root option, no host network mode | Per-task egress enforcement when networking is enabled |
| GuestRealizationReceipt | Structural consistency between the requested OCI plan, artifact identity and launch-contract fields | Actual runtime rootless/read-only/no-host-network state or cryptographic authenticity of the observation source |
| WorkloadIdentity | Holon + guest-plan digest + artifact identity + launch-authority digest | That the network policy is attached to the intended live cgroup |
| NetworkPolicyPlan | Exact workload-scoped declared egress; host ingress/forward default deny; no reasoning authority | Workload egress is still marked declared, not runtime-enforced |
| NetworkEnforcementPlan | Exact rules, required kernel hooks, cgroup bindings and fail-closed runtime proof contract | It is not activated by compilation or by lab readiness |
| AuthorityVerifier | Ed25519 signature over an exact action, subject, Holon and audience | Replay consumption or actual execution; the participant must consume the replay key atomically |

## 3. AgentTaskNetworkContract

The new `agent_workload` module binds:

- one human-readable Holon / tenant identifier and its domain-separated digest;
- one task ID, agent-principal digest, and full task-plan digest;
- one OCI S2 guest plan, a re-derived plan-consistency GuestRealizationReceipt, and the immutable artifact identity;
- one opaque OciRuntimeConsistencySnapshot from the Linux Podman/procfs observer, bound to container/image identity, process-start time, cgroup, namespaces, host boot/machine identity, and observer sequence;
- one WorkloadIdentity whose guest plan, artifact and launch-contract digests match;
- exactly one workload in the candidate NetworkPolicyPlan;
- an opaque VerifiedPolicyContainment token, generated by rerunning the finite-set checker, that binds the exact owner-boundary digest, candidate policy digest, approved prover version and report digest;
- the candidate policy digest, compiled enforcement-plan digest and allowed-destination-set digest;
- issuance time, expiry (maximum 15 minutes), and nonce digest;
- schema/kind v3 and an explicit status of runtime-observed-not-enforced-v3.

The owner-signable challenge uses AuthorityAction::NetworkActivate and signs the digest of the entire v3 contract, including the containment boundary digest, report digest, prover version, independent OCI snapshot digest, container/process identity, cgroup and boot epoch. The candidate policy must match the opaque token's candidate-policy digest; a token from a prior or different candidate is rejected before a challenge is produced. A changed task, principal, artifact, workload, policy, boundary, report, prover or expiry changes the subject and invalidates an earlier signature. The owner must review and authorize the boundary digest as part of this exact subject.

The contract also carries the machine-readable receipt scope `plan-consistency-and-artifact-identity-only-not-runtime-isolation-proof-v1`. This is required because the current `observe_oci` adapter checks the image digest but populates rootless, host-network, read-only and mount observations partly from the requested plan. It does not independently inspect the live container configuration. The receipt can bind the requested artifact and launch plan, but it must not be used as runtime isolation proof.

The nonce entropy passed to the constructor must come from the host OS CSPRNG. This module does not generate entropy or consume the replay key. The participant must atomically consume the verifier's replay key immediately before any consequential act.

## 4. High-risk workload profile v0.1

The initial contract deliberately supports a narrow profile:

- OCI S2 only, rootless Podman, read-only root, no host network;
- zero host filesystem mounts, devices, raw secrets or privileged capabilities;
- no host PID, host-root write, Docker socket or Nix daemon access;
- one tenant / one task / one workload identity per contract;
- egress only, TCP or UDP, explicit ports, maximum 32-port span;
- explicit canonical IPv4/IPv6 CIDRs only; all-address routes and hostname entries are rejected;
- no ingress or listen capabilities;
- guest network permission must agree with whether any egress capabilities are declared;
- unresolved rules, a mismatched compiled plan, fail-open state, or a reasoning-authority claim are rejected.

Why hostnames are rejected: the current compiler does not have an authenticated resolution binding. DNS changes, CNAME chains, rebinding, redirects, proxies and the final connect destination must be bound to one resolution/connection policy before hostname egress can safely be admitted. Silently resolving a hostname during compilation would not solve rebinding at connection time.



## 5. Policy containment proof (introduced in v2, required in v3)

The task contract no longer accepts only a declared candidate policy. Its constructor requires a VerifiedPolicyContainment value from verify_policy_within_boundary(boundary, candidate). The contract checks that the token's candidate digest equals the exact NetworkPolicyPlan digest and that its prover version is the approved nixward-network-policy-containment-v0.1 implementation. It then embeds the boundary digest, report digest and prover version in the task-contract subject.

The owner signature over the complete task contract therefore covers both the candidate policy and the boundary against which it was checked. Reusing a token after candidate policy mutation is rejected. Exceeds, Unsupported and Inconclusive outcomes cannot produce the required token.

This improves authorization review but does not make the boundary self-authenticating: the owner must review and authorize the boundary digest included in the contract. Nor does it prove network enforcement. The policy prover's report permanently states runtime_enforcement_proven=false; task status remains runtime-observed-not-enforced-v3 and the enforcement plan remains disabled pending independent runtime enforcement evidence.



## 6. Independent OCI observation is a required v3 input

The task contract constructor now requires an opaque OciRuntimeConsistencySnapshot from the Linux observer. The collector runs an explicitly configured Podman executable, reads Podman info/inspect, independently reads host procfs process status/stat/cgroup/mountinfo/UID/GID maps/namespace links, and collects host boot and machine identity. It takes two observations using one monotonic clock and rejects any change in container ID, image, PID start-time, cgroup, namespace inodes, mappings, mountinfo digest, Podman executable digest, or host boot/machine identity during the collection window.

The task contract checks that the snapshot's image matches the exact OCI plan; source agreement and temporal stability are true; the root mount is read-only; no_new_privs is set; effective capabilities are zero under the strict profile; Podman reports no extra mounts, host network, host PID or privileged mode; and the snapshot itself does not claim runtime enforcement. It embeds the snapshot digest, container ID, PID/start-time, cgroup, boot ID, machine-ID digest and observer sequence into the complete owner-signable contract subject.

This is a bounded source-consistency token, not a cryptographic host attestation. Podman info and inspect come from the same runtime; the Podman binary is hashed before/after invocation but the collector does not prove which inode the kernel executed or attest the Podman daemon/helper binaries. Procfs and kernel integrity remain trust assumptions. A signature over this snapshot would authenticate the observer key and bytes, not make false kernel claims true. The snapshot also does not prove that a cgroup/BPF/network policy is attached or that isolation remains true after the collection window.

## 7. Critical non-claims

This v0.1 contract does **not**:

- run an agent, launch a guest, or attach a cgroup/BPF program;
- prove that a source observation is cryptographically authentic merely because it is structurally valid;
- prove production egress enforcement or task isolation from a test fixture;
- implement a DNS, redirect, proxy, TLS-SNI or QUIC policy;
- implement dynamic lease issuance/revocation or replay-key consumption;
- grant Symthaea host shell access or automatic remediation authority.

The network-enforcement plan must remain `disabled-until-runtime-proof-v40`. A passing runtime-lab report is only backend maturity evidence; target-host feature probes, exact cgroup bindings and a separate owner-authorized activation path are still required.

## 8. Tests added

Fifteen task-contract Rust unit tests cover:

1. exact one-tenant / one-task / one-artifact / one-policy binding;
2. wildcard CIDR rejection;
3. hostname rejection without a resolution proof;
4. invalid and non-canonical CIDR rejection;
5. wrong workload binding;
6. substituted guest-receipt rejection;
7. owner signature over the complete task-bound network contract;
8. task mutation invalidating the earlier owner signature;
9. expiry rejection;
10. host mount and unsafe guest profile rejection;
11. expanded IPv6 default-route rejection;
12. stale policy-proof rejection after candidate policy mutation;
13. runtime snapshot substitution rejection when the image identity differs;
14. runtime process-start mutation invalidating the owner signature;
15. rejection of a runtime snapshot bound to a different task cgroup.

The task-binding branch includes the finite-set network_containment module and the Linux OCI procfs observer. Schema-v3 AgentTaskNetworkContract requires both the opaque VerifiedPolicyContainment token and an OciRuntimeConsistencySnapshot. The current source corpus is 15 task-contract tests, 24 policy-containment tests, 27 OCI-observer tests, 13 receipt-chain tests and 15 signed-checkpoint tests. All are source-level only until executed with the pinned Rust toolchain. The separate signed-checkpoint prototype verifies Ed25519 signatures against an externally supplied trust record, verifier nonce, exact snapshot/chain digests, previous checkpoint digest, key generation/revocation and sequence/time expectations. It is not consumed by the task contract and does not establish hardware-backed attestation or durable checkpoint storage. No compile, clippy, formatting, Nix evaluation, live Podman collection, durable receipt-chain persistence, external anchoring, runtime-lab or CI pass is claimed here.

### Signed observer-checkpoint prototype (26 Nov 2026)

A separate `observe::signed_checkpoint` module now signs a deterministic, domain-separated checkpoint with Ed25519 and verifies it against a relying-party-supplied trust record and expectation. The payload binds observer/key identity and generation, machine/boot identity, sequence, exact snapshot and chain-head digests, previous accepted checkpoint digest, verifier nonce digest, issuance and expiry. The verifier rejects revoked/expired keys, stale or future checkpoints, nonce mismatch, key-generation changes, machine/observer substitution, parent/sequence rollback, and snapshot/chain digest substitution. Both serialized envelope and payload reject unknown fields.

The module returns an opaque `VerifiedOciObserverCheckpoint`, but the task contract does not consume it. The verifier caller must independently verify the snapshot and receipt chain before supplying their exact digests, generate and consume the nonce, and persist the returned checkpoint digest/sequence outside the workload. No persistent store, key enrollment/distribution, remote witness, measured boot, hardware key or runtime enforcement is implemented. This is a software-authenticated checkpoint prototype, not a host attestation.

See [OCI_OBSERVER_SIGNED_CHECKPOINT_V0_1.md](OCI_OBSERVER_SIGNED_CHECKPOINT_V0_1.md). Its 15 source-level tests bring the overall branch corpus to 94 functions; none is compiled or executed.

## 9. Next qualification increments

### P0 — source and artifact authenticity
Bind the local guest inspection to an authenticated Nixward host receipt and exact machine/boot identity. Verify registry signature/provenance and OCI digest before guest start. Never treat a tag or self-reported digest as authority.

### P1 — per-task egress enforcement
Extend the runtime backend so exact task cgroups—not merely workload-plan identities—are bound to the live task. Add negative tests for cgroup swap, policy update race, process migration, alternate network namespace, UDP, IPv6, proxy bypass and enforcer restart.

### P2 — authenticated name resolution
Add a resolution contract binding hostname, DNSSEC/trusted resolver policy, answer set, TTL, CNAME chain, resolver identity, task/policy digest, and connection-time destination. Revalidate redirects and connect targets. Where L7 semantics matter, use a separately authenticated egress proxy rather than pretending an L3 CIDR allowlist validates HTTPS hostnames.

### P3 — isolated runtime replay
Run only synthetic fixtures in a disposable NixOS VM. Record target-host kernel probes, cgroup identity, actual packet allow/deny receipts, process lineage, guest observation and independent service oracle. A model statement such as `blocked=true` is never a receipt.

### P4 — task security benchmark
Use Platform ATR-001..ATR-039 and report hard-gate effects, task completion, false refusals, false assurance, attribution, p50/p95 detection and containment, resource budget and provenance. Keep evaluator-private ground truth outside the candidate boundary.

## 10. External alignment

- OASB-1 / OASB Eval: map identity/provenance, capability authorization, supply chain, credential protection, operational controls and monitoring. Do not reuse self-labelled benign samples to estimate false-positive rates.
- IETF draft `draft-hcf-bpm-agent-security-benchmark-profiles-00`: declare the system-under-test boundary and scenario profile with every metric; its status is work in progress, not a final standard.
- MITRE ATT&CK Evaluations: map technique coverage, detection/protection outcomes and source-of-action disclosure, but compare only matched configurations and scenarios.
- AgentDojo / indirect-injection work: report attack success and legitimate-task utility together; safe abandonment is not successful task completion.

## 11. Claim ceiling

The correct current claim is narrow:

**Nixward now has a typed, expiring, owner-signable schema-v3 contract that binds one OCI guest plan, a bounded Podman/procfs source-consistency snapshot, one tenant workload, and an opaque proof that the candidate network policy is within an owner-supplied boundary. The snapshot is not a signed host attestation, and the contract does not prove active network enforcement.**

This is not evidence that production network enforcement is active. That requires the target/runtime qualification sequence above.


Source-level regression controls: IPv4/IPv6 `/0` CIDRs are rejected by numeric prefix semantics; stale policy proofs, mismatched runtime image snapshots, declared binds/tmpfs, shared cgroup/network/PID modes, missing seccomp filter mode and any nonzero capability set under the strict profile are rejected. The task-binding branch contains 15 task-contract tests, 24 policy-containment tests, 27 OCI-observer tests and 13 receipt-chain tests (79 total source-level test functions). None has been compiled or executed.
